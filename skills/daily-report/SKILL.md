# 日报编排

默认工作流只有思源笔记 MCP 日报存储端。日报的推送（创建/写入）、追加、修改、查询和获取全部通过思源笔记 MCP。公司系统写入端与最终提交端是可选的后续流程，只在用户明确要求时启用；二者可能是 `same_tool` 或 `separate_tools`，也可能位于同一运行端或分开的运行端。配置字段见 [references/workflow-config.md](references/workflow-config.md)。

## 操作意图路由

- 用户只说“推送”“推送日报”“保存日报”“写入日报”或称当前环境为“推送端”时，只执行思源日报存储阶段。不得要求公司系统工具、目标表单、字段映射或提交成功凭证。
- 思源写入经过严格预检并按同日期路径精确回读一致后即可报告推送成功。此处的“推送成功”只表示日报已写入思源，不等于公司系统“已提交”。
- 查询、获取、创建、追加和修改同样只使用思源 MCP，不因缺少公司系统能力而停止。
- 只有用户明确要求写入或提交公司系统，例如明确说“填写公司系统”“写入公司日报”“提交公司日报”或“最终提交”，才进入公司系统阶段并读取对应配置。
- 即使已经保存公司系统配置或 `auto_submit_after_write=true`，普通思源推送也不得自动进入公司系统；该选项只在当前请求已明确进入公司系统流程后生效。

## MCP 发现优先

每次启动本 Skill 时，先发现并初始化思源 MCP，再读取本地 `workflow` 配置。优先使用当前会话已暴露的思源 MCP 工具；若工具尚未出现在会话中，先按已配置的 MCP 连接执行一次初始化或重连，并检查鉴权与工具列表。`workflow` 配置缺失不等于思源 MCP 不可用，不能因为配置文件不存在就直接报告“没有思源 MCP”。必须区分配置缺失、未初始化、鉴权失败和连接失败；只有确认连接配置不存在或初始化/鉴权确实失败后，才能报告 MCP 不可用。不得输出或记录 MCP 令牌。

## 首次确认与持久化

先读取 `${DAILY_REPORT_CONFIG:-~/.config/daily-report/config.json}` 中的 `workflow`。只询问缺失且会影响本次操作的决定；用户明确回答后立即持久化，后续不再重复询问。可以把相互关联的缺失项合并成一次简短提问，但不能用默认猜测代替用户决定。

普通思源日报操作只按需确认：明确日期、目标笔记本与路径、思源 MCP 读写能力、当前操作授权，以及固定必填字段；首次生成本周总结时再确认使用全部项目还是指定项目。不要询问公司系统相关信息。

仅当用户明确进入公司系统流程时，再按需确认：

1. `workflow_mode`：角色位于 `same_runtime` 还是 `separate_runtimes`。
2. `local_roles`：当前运行端是否承担公司系统写入端或最终提交端。
3. `company_action_mode`：公司系统写入与最终提交使用 `same_tool` 还是 `separate_tools`。
4. 公司系统工具、目标位置、模板、字段映射、写入成功凭证与最终提交成功凭证。
5. 是否在公司系统写入成功后自动继续最终提交，以及成功后是否回写思源状态。

配置完整时直接复用。用户本次明确指定的日期、项目、工具或映射只覆盖本次，除非用户明确要求保存。

## 已停用旧链路

本 Skill 只支持思源笔记 MCP 直连。旧版服务地址、角色密钥、租约状态和相关客户端不属于有效配置；发现这些旧字段或旧配置文件时立即删除，不读取、不迁移、不回退，也不提供兼容入口。

配置只保存逻辑工具标识、目标、字段映射、成功条件、授权状态和偏好。实际密钥、令牌、密码只能保存在对应工具、环境变量或凭据管理器中；配置最多保存 `credential_ref`，不得保存秘密本身。配置目录权限为 `0700`，文件权限为 `0600`；更新时保留未知字段，原子写入后回读验证。

持久授权不覆盖高风险动作：删除、移动、批量替换、修改权限等仍按当前工具要求再次确认。工具要求严格安全写入时，执行预检，使用新的请求 ID 和服务端返回的前置条件，完成后按稳定路径或 ID 精确回读。

## 日期与日报存储

- 必须严格按日期执行，不得用相邻日期或最近一篇替代。
- 所有读取、创建、追加、修改、写入公司系统和最终提交都必须绑定明确的 `YYYY-MM-DD`。未给日期时先询问，不能用“最新”“最近”或其他日期代替。
- 默认时区为 `Asia/Shanghai`，默认思源路径为 `/工作/daily note/YYYY/MM/YYYY-MM-DD`，实际持久化配置优先。
- 日报创建、追加、修改、查询和获取必须调用思源笔记 MCP；思源 MCP 是唯一日报存储入口。只在已配置的个人日报笔记本和目标日期精确路径内查询，不跨笔记本搜索他人的日报，不得搜索或选择最新日报。
- 今天的日报可使用每日笔记创建动作；补写历史日报使用明确日期路径。创建、追加或修改前先读取完整目标，写入后精确回读。
- 普通推送以同日期思源文档的精确回读结果作为成功凭证；成功后报告“已推送到思源”或“已写入思源”，不要写成“已提交”。

### 固定必填字段

每一条日报事项都必须包含以下四项，缺一不可。每条事项独立成块，字段分行，事项之间空一行；不要使用 `｜` 把所有字段压在同一行。

```markdown
### 1. 日报事项

- 日期：YYYY-MM-DD
- 客户/项目名称：名称
- 完成进度：已完成/进行中（可附百分比）
- 工作内容：简明总结
```

编号、日期、完成进度、客户/项目名称是固定要求，不能通过配置取消。无法从当前项目、任务或日报内容确认某项时，先询问用户，不得猜测或留空。多条内容按 `### 1.`、`### 2.` 分块编号；内容是结果性总结，不是任务流水账。已有日报采用旧的紧凑单行格式时，修改或追加时应顺手整理为上述分块格式，但不得改变原有事实内容。

## 本周项目与任务

第一次生成本周总结时询问“使用本周全部项目，还是指定项目？”。选择后写入 `project_scope`，以后自动复用，不再询问目录。用户临时指定项目时只覆盖本次。按 `Asia/Shanghai` 统计本周一 `00:00` 至当前时间，将同项目同状态事项合并成简明结果；不能验证的状态不猜测。

## 按需写入公司系统

只有用户明确要求写入公司系统时，才读取精确日期的思源日报，并按已确认的模板和 `field_mapping` 填写公司系统。写入成功必须取得 `write_success_evidence`，例如草稿记录 ID、已保存状态或精确回读结果。写入成功不等于最终提交成功。

如果写入结果失败、超时或不确定，先查询同日期、同目标记录，禁止重复填写。若确认已写入但尚未最终提交，可在获授权时回写“已写入待提交”及非敏感记录引用，不能写成“已提交”。

## 按需最终提交

当前请求已经明确进入公司系统流程，且 `auto_submit_after_write=true`、当前授权允许、最终提交端可用时，写入验证成功后自动继续最终提交，不再重复询问。`same_tool` 仍要区分写入和提交两个阶段；`separate_tools` 通过已确认的 `handoff_mode` 传递日期、目标记录引用和必要的非敏感内容，不传递秘密。

最终提交必须取得 `submit_success_evidence`，例如提交记录 ID、明确成功状态或可回读的已提交结果。只有最终提交成功，才在同一日期的思源日报中追加或更新“已提交”标记，并回读验证。提交失败、超时或结果不确定时不写“已提交”，先查询下游状态；已有同日期、同目标系统的“已提交”记录时默认停止，不得重复提交。

## 阶段边界

- 缺少当前明确请求阶段的工具、目标、授权、字段映射或成功凭证定义时，只询问该阶段缺失项；不得以未被请求的公司系统阶段缺少配置为由阻断思源推送。
- 思源推送成功、公司系统写入成功、最终提交成功、思源状态回写成功是四个独立结果，分别验证并报告。
- 分开的运行端只执行 `local_roles` 中的阶段；完成后输出下一阶段所需的日期、非敏感正文或记录引用。不得声称另一个运行端已经执行。
- 任一阶段结果不确定时先精确回读，禁止换用另一日期或另一份“最新日报”，也禁止直接重试造成重复写入或重复提交。
