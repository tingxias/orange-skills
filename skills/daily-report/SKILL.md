# 日报编排

默认工作流只有思源笔记 MCP 日报存储端。日报的推送（创建/写入）、追加、修改、查询和获取全部通过思源笔记 MCP。公司系统写入端与最终提交端是可选的后续流程，只在用户明确要求时启用；二者可能是 `same_tool` 或 `separate_tools`，也可能位于同一运行端或分开的运行端。配置字段见 [references/workflow-config.md](references/workflow-config.md)。

## 操作意图路由

- 用户只说“推送”“推送日报”“保存日报”“写入日报”或称当前环境为“推送端”时，只执行思源日报存储阶段。不得要求公司系统工具、目标表单、字段映射或提交成功凭证。
- 思源写入经过严格预检并按同日期路径精确回读一致后即可报告推送成功。此处的“推送成功”只表示日报已写入思源，不等于公司系统“已提交”。
- 查询、获取、创建、追加和修改同样只使用思源 MCP，不因缺少公司系统能力而停止。
- 只有用户明确要求写入或提交公司系统，例如明确说“填写公司系统”“写入公司日报”“提交公司日报”或“最终提交”，才进入公司系统阶段并读取对应配置。
- 即使已经保存公司系统配置或 `auto_submit_after_write=true`，普通思源推送也不得自动进入公司系统；该选项只在当前请求已明确进入公司系统流程后生效。

## MCP 发现优先

每次启动本 Skill 时，先发现并初始化思源 MCP，再读取本地 `workflow` 配置。思源 MCP 名称必须由用户首次明确确认，推荐默认名称为 `siyuan-sisyphus`；推荐值只是待确认选项，不能在用户未确认时当成已配置。用户确认后立即持久化到 `report_store.mcp_name`，同时写入 `mcp_name_confirmed=true`，后续直接复用该名称，不再重复询问。只有名称存在且确认状态为 `true` 才视为已完成首次确认；缺少确认状态时仍需询问用户。

优先查找当前会话是否已暴露与 `report_store.mcp_name` 同名的思源 MCP 工具；若工具尚未出现，先按该名称对应的 MCP 连接执行一次初始化或重连，并检查鉴权与工具列表。存在连接配置但当前会话找不到同名工具时，明确报告“已配置思源 MCP 名称，但当前会话未暴露该 MCP 工具”，不能使用“原生工具未启用”等含糊表述。`workflow` 配置缺失不等于思源 MCP 不可用，不能因为配置文件不存在就直接报告“没有思源 MCP”。必须区分配置缺失、未初始化、鉴权失败和连接失败，并进一步区分名称未确认与当前会话未暴露工具；只有确认连接配置不存在或初始化/鉴权确实失败后，才能报告 MCP 不可用。不得输出或记录 MCP 令牌。

## 首次确认与持久化

先读取 `${DAILY_REPORT_CONFIG:-~/.config/daily-report/config.json}` 中的 `workflow`。只询问缺失且会影响本次操作的决定；用户明确回答后立即持久化，后续不再重复询问。可以把相互关联的缺失项合并成一次简短提问，但不能用默认猜测代替用户决定。

普通思源日报操作只按需确认：首次明确确认思源 MCP 名称（推荐 `siyuan-sisyphus`）、明确日期、目标笔记本与路径、思源 MCP 读写能力、当前操作授权，以及固定必填字段；首次生成本周总结时再确认使用全部项目还是指定项目。不要询问公司系统相关信息。

仅当用户明确进入公司系统流程时，再按需确认：

1. `workflow_mode`：角色位于 `same_runtime` 还是 `separate_runtimes`。
2. `local_roles`：当前运行端是否承担公司系统写入端或最终提交端。
3. `company_action_mode`：公司系统写入与最终提交使用 `same_tool` 还是 `separate_tools`。
4. 公司系统工具、目标位置、字段映射、写入成功凭证与最终提交成功凭证。模板未配置时直接使用默认模板“工作日报-鲁中客成-运维”，不为默认模板单独提问。
5. 是否在公司系统写入成功后自动继续最终提交，以及成功后是否回写思源状态。

配置完整时直接复用。用户可以修改模板名称；明确修改后立即持久化并在后续直接复用。用户本次明确指定的日期、项目、工具或映射只覆盖本次，除非用户明确要求保存。

## 已停用旧链路

本 Skill 只支持思源笔记 MCP 直连。旧版服务地址、角色密钥、租约状态和相关客户端不属于有效配置；发现这些旧字段或旧配置文件时立即删除，不读取、不迁移、不回退，也不提供兼容入口。

配置只保存逻辑工具标识、目标、字段映射、成功条件、授权状态和偏好。实际密钥、令牌、密码只能保存在对应工具、环境变量或凭据管理器中；配置最多保存 `credential_ref`，不得保存秘密本身。配置目录权限为 `0700`，文件权限为 `0600`；更新时保留未知字段，原子写入后回读验证。

持久授权不覆盖高风险动作：删除、移动、批量替换、修改权限等仍按当前工具要求再次确认。工具要求严格安全写入时，执行预检，使用新的请求 ID 和服务端返回的前置条件，完成后按稳定路径或 ID 精确回读。

## 日期与日报存储

- 必须严格按日期执行，不得用相邻日期或最近一篇替代。
- 所有读取、创建、追加、修改、写入公司系统和最终提交都必须绑定明确的 `YYYY-MM-DD`。未给日期时先询问，不能用“最新”“最近”或其他日期代替。
- 先分别确定“目标日报日期”和“统计范围”，两者是独立参数。目标日报日期决定读取和写入哪一天的思源文档；统计范围只决定从项目记录中筛选哪些工作内容，不能反向改变目标日报日期。
- 用户明确指定日期时，目标日报日期始终使用该日期。用户说“昨天的日报”或“补昨天日报”时，按 `Asia/Shanghai` 写入昨天；用户说“截至昨天的本周总结”时，统计范围为本周一至昨天，并写入昨天。执行当天只能用于计算相对日期，不能自动成为目标日报日期。
- 默认时区为 `Asia/Shanghai`，默认思源路径为 `/工作/daily note/YYYY/MM/YYYY-MM-DD`，实际持久化配置优先。
- 日报创建、追加、修改、查询和获取必须调用思源笔记 MCP；思源 MCP 是唯一日报存储入口。只在已配置的个人日报笔记本和目标日期精确路径内查询，不跨笔记本搜索他人的日报，不得搜索或选择最新日报。
- 今天的日报可使用每日笔记创建动作；补写历史日报使用明确日期路径。不得为了容纳统计范围而创建统计结束日之外的日报，也不得先写入执行当天再回头纠正日期。
- 普通推送以同日期思源文档的精确回读结果作为成功凭证；成功后报告“已推送到思源”或“已写入思源”，不要写成“已提交”。

## 数据源与统计范围

- 用户要求读取“当前项目”“项目记录”“项目任务”或“项目对话”时，默认数据源是当前工具可见的项目对话记录和任务记录。先列出实际可访问的项目，再按已保存的 `project_scope` 使用全部项目或指定项目。
- 按本次统计的目标工作日逐项目检查对话记录；没有今天的对话记录时直接跳过项目（历史日期场景中的“今天”按本次统计目标工作日解释），不生成空项目块、不生成空的今日工作项目块，也不生成该项目的明日计划条目。项目只有任务记录但没有该日对话时同样跳过，不追问、不补齐、不回退到 Git、不把其他日期或最近对话当作当天内容。
- 只有用户明确要求读取 Git、提交记录、工作区变更或代码状态时才使用 Git；不得自行改用 Git，也不得用 Git 摘要替代项目对话记录和任务记录。当前工具无法读取项目对话或任务时，明确报告缺少该能力并询问用户，不能静默回退到 Git。
- “昨天的工作内容”只统计昨天；“截至昨天的本周总结”统计本周一 `00:00` 至昨天 `23:59:59`；用户指定其他起止日期时使用其明确范围。所有边界均按 `Asia/Shanghai` 计算。
- 统计范围只用于筛选数据和结果回执，不得写入日报正文或标题。不得生成“对话记录补充（起止日期）”“本周汇总（起止日期）”等来源性标题；日报正文只保留项目块和实际工作内容。
- 第一次生成本周总结时询问“使用本周全部项目，还是指定项目？”。选择后写入 `project_scope`，以后自动复用，不再询问目录。用户临时指定项目时只覆盖本次；不能验证的状态不猜测。

### 固定结构与必填字段

推送到思源的日报正文固定分为“今日工作”和“明日计划”两个完全独立的区域。“明日计划”不能嵌套到任何项目块中，也不能与“今日工作”的工作内容混写。

“今日工作”中的每一条日报事项都必须包含以下四项，缺一不可。每条事项独立成块，字段分行，事项之间空一行；不要使用 `｜` 把所有字段压在同一行。

```markdown
## 今日工作

### 1. qicheng

- 日期：YYYY-MM-DD
- 客户/项目名称：qicheng
- 完成进度：已完成/进行中（可附百分比）
- 工作内容：
  1. 简明结果一
  2. 简明结果二

## 明日计划

1. 【qicheng】计划事项一
2. 【orange-skills】计划事项二
```

编号、日期、完成进度、客户/项目名称是今日工作项目块的固定要求，不能通过配置取消。无法从当前项目、任务或日报内容确认某项时，先询问用户，不得猜测或留空。标题必须是 `### {number}. {customer_or_project}`，不能使用“日报事项”或数据来源作为标题。同一项目的多条工作合并为一个项目块，工作内容在项目块内按序号列出；内容是结果性总结，不是任务流水账。不同项目按 `### 1.`、`### 2.` 分块编号。

“明日计划”区域必须独立编号，每项写成 `序号. 【客户或项目名称】计划内容`。其中“明日”始终相对于日报日期计算，不是相对于实际执行当天计算；无法确认计划内容或所属项目时先询问用户。写入公司系统时，将整个明日计划区域作为一个独立值映射到模板的明日计划字段，不拆入今日工作项目块。

## 创建、追加与修改

- 创建、推送、追加或修改前，先按目标日报日期完整读取并保存原文快照。目标文档不存在时才创建；目标文档已经存在时，普通“推送”或“写入”默认按项目合并，不得把现有文档当成空白重新生成。
- 追加必须保留全部原有内容：今日工作中同一项目合并到已有项目块的“工作内容”末尾并继续编号，不同项目追加新的项目块；明日计划只追加到独立的“明日计划”区域并继续该区域编号。完全相同的工作内容或计划不重复追加。
- 无当天对话而被跳过的项目只从本次新增输入中排除，不得因此删除或改写目标日报中已有的历史项目、计划或状态标记。
- 修改只修改用户指定的项目或事项；用户指定修改明日计划时，只修改对应计划。保留全部原有内容中的其它项目、标题、字段、正文和状态标记。已有内容采用旧格式时，只整理本次明确修改的区域；除非用户明确要求，不得顺手重排或改写整篇日报。
- 只有用户明确要求“覆盖”“重写”或“清空”目标日期日报时，才允许替换全文；删除、清空和批量替换仍需遵守当前工具的高风险确认要求。
- 写入前比较原文快照与候选正文，确认原有非目标内容没有减少或发生意外变化；无法证明保留时停止写入。写入后完整回读，再次确认原有非目标内容、目标修改和项目编号均正确。工具只支持整篇替换时，也必须用保留原文后的完整候选正文执行，不能只提交新增片段覆盖原文。

## 按需写入公司系统

只有用户明确要求写入公司系统时，才读取精确日期的思源日报。默认模板名称为“工作日报-鲁中客成-运维”；用户可以修改模板名称，修改后立即持久化并在后续直接复用。按模板和 `field_mapping` 填写公司系统时，只要本阶段所需的日期、工具、目标、字段映射、授权和成功凭证定义齐全，就不再询问是否写入，直接执行写入。缺少必要信息时只询问缺失项，不能把补齐信息的问题变成一次额外的“是否写入”确认。

写入成功必须取得 `write_success_evidence`，例如草稿记录 ID、已保存状态或精确回读结果。写入成功不等于最终提交成功。直接写入只适用于用户当前已明确要求的公司系统写入，不自动授权最终提交、删除、覆盖、批量替换或权限修改。

如果写入结果失败、超时或不确定，先查询同日期、同目标记录，禁止重复填写。若确认已写入但尚未最终提交，可在获授权时回写“已写入待提交”及非敏感记录引用，不能写成“已提交”。

## 按需最终提交

当前请求已经明确进入公司系统流程，且 `auto_submit_after_write=true`、当前授权允许、最终提交端可用时，写入验证成功后自动继续最终提交，不再重复询问。`same_tool` 仍要区分写入和提交两个阶段；`separate_tools` 通过已确认的 `handoff_mode` 传递日期、目标记录引用和必要的非敏感内容，不传递秘密。

最终提交必须取得 `submit_success_evidence`，例如提交记录 ID、明确成功状态或可回读的已提交结果。只有最终提交成功，才在同一日期的思源日报中追加或更新“已提交”标记，并回读验证。提交失败、超时或结果不确定时不写“已提交”，先查询下游状态；已有同日期、同目标系统的“已提交”记录时默认停止，不得重复提交。

## 阶段边界

- 缺少当前明确请求阶段的工具、目标、授权、字段映射或成功凭证定义时，只询问该阶段缺失项；不得以未被请求的公司系统阶段缺少配置为由阻断思源推送。
- 思源推送成功、公司系统写入成功、最终提交成功、思源状态回写成功是四个独立结果，分别验证并报告。
- 分开的运行端只执行 `local_roles` 中的阶段；完成后输出下一阶段所需的日期、非敏感正文或记录引用。不得声称另一个运行端已经执行。
- 任一阶段结果不确定时先精确回读，禁止换用另一日期或另一份“最新日报”，也禁止直接重试造成重复写入或重复提交。
